# C2 Stripe implementation references

Checked against official documentation on 2026-10-11. This is an implementation reference, not evidence of real sandbox payments. The user has no Stripe test account available for this phase; use transport fixtures and explicitly record that external test gap.

- Pin request `Stripe-Version: 2026-09-30.endive`, the current documented version. Configure the eventual webhook endpoint with the same version; account defaults and request version do not retroactively transform events. [Versioning](https://docs.stripe.com/api/versioning)
- Subscription period boundaries are on `items.data[].current_period_start/end`; this product expects exactly one configured monthly Price and quantity one. Retrieve `latest_invoice` and verify its customer, subscription parent, mode and paid status. Do not use invoice top-level `period_end` as the paid service period. [Subscription](https://docs.stripe.com/api/subscriptions/object), [Invoice](https://docs.stripe.com/api/invoices/object)
- Current invoices expose payment records through `/v1/invoice_payments?invoice=...`. Payment records identify the PaymentIntent (and other supported payment types); follow canonical objects to their charge and validate relationships/mode. Handle pagination explicitly or fail the synchronization rather than silently truncating risk assessment. [Invoice payments](https://docs.stripe.com/api/invoice-payment/list), [Payment object](https://docs.stripe.com/api/invoice-payment/object)
- Expanded definitions confirm invoice `parent.type=subscription_details` and `parent.subscription_details.subscription`; invoice payment `payment.type` is `payment_intent`, `charge` or `payment_record`. A PaymentIntent supplies `latest_charge`; direct charge records are possible. Unsupported external payment records must fail verification safely rather than bypass refund checks. Dispute listing accepts a `charge` filter. [Invoice parent](https://docs.stripe.com/api/invoices/object?query=parent), [Payment details](https://docs.stripe.com/api/invoice-payment/object?query=payment), [PaymentIntent charge](https://docs.stripe.com/api/payment_intents/object?query=latest_charge), [Dispute filters](https://docs.stripe.com/api/disputes/list?query=)
- Charges contain captured/refunded amounts and dispute indication. Retrieve current dispute state for a disputed current-invoice charge; historical invoice risks must not freeze a newer paid period. Bound object traversals and never persist card details or whole provider bodies. [Charge](https://docs.stripe.com/api/charges/object), [Disputes](https://docs.stripe.com/api/disputes/list)
- Stripe events have no guaranteed delivery order; timestamps alone cannot deduplicate or order them. Persist event IDs and reconcile current provider objects. [Webhook delivery](https://docs.stripe.com/webhooks)
- A hosted Checkout session expires between 30 minutes and 24 hours after creation. Local lease expiry is not proof of provider session expiry; reconcile the saved session or recover uncertain creates before allowing another checkout. Persistent idempotency keys must not be casually replaced on retry. [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create)

The implementation must verify current shapes with the official reference for any additional nested field used. No community examples override the pinned API shape. C3 remains deferred; production account onboarding, prices and live endpoint delivery are not part of this phase's claimed evidence.
