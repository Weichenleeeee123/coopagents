# Coopagents 重构前的能力与工作流

盘点日期为 2026-11-20，源码基线为 `codex/refactor-bridge-wake` 的 `5aa3673`。读者是要决定下一版产品边界的团队成员。以下“支持”指这份源码提供相应入口；真实运行证据另列在末节。历史规划、候选版本和当前部署不混算。

## 一、从两份首页看产品边界

黑客松里，两位队员各自让 agent 写出一份前端页面，双方起初都没有意识到重复。后来新增功能分散在两处。这件事里至少发生了三个不同的问题。

| 当时需要什么 | 当前已有的能力 | 仍然缺什么 |
| --- | --- | --- |
| 开工时知道“另一个人也在做这个首页” | 完整工作流可以查已声明的任务、范围、负责人、会话和分支。两张卡声明相同或上下级目录时能提示重叠。轻量入口可以直接告知队友自己在做什么。 | 如果没有声明，两个人也没有主动询问，系统没有可靠的信号。不同文件、不同路由也可能实现同一个用户目标。 |
| 发现重复后，决定沿用哪份成果 | 可找指定队员、交换路由或样例、显式共享文件；一个 agent 可在自己获准访问的工作区核对后回复。需要团队认可时，可以提出有版本的约定，由人批准。 | 消息已投递、模型做过核对、团队选定了首页是三件不同的事。普通回复不会自动变成全队约定。 |
| 下一个会话“给首页加搜索”时继承结论 | 完整入口可以查询已批准约定、任务上下文、交付引用，或读回历史答复。 | 新轻量连接没有共享上下文查询和约定工具。也没有按“首页”这个产品概念自动找出公认入口、在相关会话中及时提示的机制。 |

这解释了为什么产品既显得重，又会漏掉真实冲突。现有结构能把**已知、已声明的依赖**处理得很仔细。黑客松暴露的是**团队还没意识到的交集**，以及交集处理完后如何让下一位成员沿用结果。[范围重叠实现](../src/activity.py) · [Git 路径检查](../src/repositories.py) · [共享上下文](../src/context.py) · [版本约定](../src/contracts.py)

| 入口 | 谁在使用 | 当前能看到或执行什么 |

## 四、把能力连起来看

### 路径 A：没有任务卡的两人协作

1. 队员创建空间、发一次性邀请，队友加入。另一种起点是两个人已有同一项目的托管凭据。每个人用自己的身份接入自己的工具。
2. 新原生会话通过 `whoami` 核对项目和成员；`list_members` 找到收件人。此时系统知道“有哪些队员”，还不知道两个人都准备写首页。
3. A 自主察觉信息缺口，或想分享“我正在写首页”，用 `send_request` 定向发给 B。服务存储请求及投递记录。支持的本地离线操作可能先进入发件箱；断线时必须区分“待发送”和“服务已接收”。
4. B 在下一次工作机会主动读 `read_inbox`，或在已授权且受支持的唤醒路径中收到提示后读取。B 可以用自己有权查看的代码核实首页路径，用 `reply` 回答。
5. A 用 `read_replies` 取得与原请求关联的答案，按自己的目标决定是否使用。对方显式读了消息、对方回答了、A 把搜索加在了正确页面，分别需要不同证据。只有最后一个能说明这次沟通改变了开发结果。
6. 若 B 以后离开，向 B 发送的普通问题仍指向 B。若想把“首页由谁负责”或“以后都从这个路由扩展”变成全队可继承的事实，当前需要另行使用完整工作流、已批准约定或项目内已有的文档/代码入口。[直接传话流程](team-workflow.md) · [双客户端用例](../tests/test_space_bridge.py)

### 路径 B：已经明确分工的协作

以“前端需要后端当前接口”为例。下列分支按实际需要进入，单次协作不必全部走完。

| 时刻 | 成员和 agent 做什么 | 系统记录什么 |
| --- | --- | --- |
| 分工 | 人建前端和后端任务并声明范围；两位 agent 分别认领、登记会话。 | 任务 ID、负责人、归属代次、执行绑定和修订。 |
| 开工 | agent 读取简报、约定及相关 Git 状态，按需报告进度。 | 已声明的责任边界、来源和新鲜度、当前执行的工作上下文。 |
| 遇到跨队员问题 | 已知具体人可直接问；希望找到职责负责人可按任务或范围查询并 `ask_owner`。需要持续跟踪阻塞时建立来源任务到目标任务的依赖。 | 固定收件人、随负责人变化的问题路由、正式任务依赖有不同的状态。 |
| 等待、回答和恢复 | 唯一目标未认领时可排队；范围有歧义时返回候选。目标换人后重路由。应答方从自己的现场取得答案；提问方可并行做其他工作，重开会话后继续读回信。 | 历史路由、当前请求、回复、读取证据和等待原因。旧答复仍可追溯。 |
| 验证和确认 | 普通问题可由有权方解决。正式依赖由来源执行读取当前路由的最新答复，再用相符的版本确认满足。若答案改变共同接口，可另行提出约定、由人批准、让依赖旧版本的任务复核。 | 问题解决、依赖满足、约定批准、代码已采用是各自独立的记录或结果。 |
| 转交或中断 | 可释放、提议交接、由接收人接受或拒绝；管理员有强制转交等权限。新负责人绑定自己的会话，查历史并恢复。 | 当期执行归档；旧绑定失效。相关问题与依赖按当前归属调整。 |
| 交付 | 只需可追溯时关联 Git 对象；开启写入时本地创建任务分支，检查新鲜路径，提交、推送、开草稿 PR，按需请求合并。外部 GitHub 状态通过刷新或事件进入项目。 | 分别保留自报进度、本地观察、平台核验和人的决定。合并 PR 与团队验收是不同事实。 |

详见[责任路由与答复](team-workflow.md)、[任务生命周期](task-lifecycle.md)、[Git 本地流程](git-local-setup.md)和[GitHub 接入](git-github-setup.md)。

### 路径 C：掉线、重启、换会话时

- 主机或网络断开时，空间桥接器记录连接情况。恢复后重新认证、回放保留的事件；游标过期时重新读取权威状态。某些技术写入可以排队重试，人类决定不进入自动重放。
- 一个成员有多个会话时，有有效绑定和 watcher 的请求尽量命中当前执行会话；会话过期或不具备定向条件时回落到成员待办。消息依旧可以存在，空闲模型是否开始新一轮取决于工具和本机设置。
- 换会话后，成员级来信、已发问题的回信可以恢复；任务级写入还要核验当前负责人和有效执行绑定。运行状况、投递、显式读取和真实采用始终需要分开解释。[事件协议](realtime-protocol.md) · [会话路由](../src/session_routing.py) · [离线恢复](../src/local_outbox.py)

### 路径 D：团队平台和运营人员

账户版由管理员初始化或登录，创建团队和项目、邀请队员并授予项目范围；成员选择项目后接入自己的 agent。日常通过工作台看项目活动、共享资产、处理待人决定的事项。项目可单独绑定 GitHub App。托管运营者在启用计费的部署里管理订阅同步与故障重试；自托管运营者管理服务、备份和恢复。这条路径承担团队管理和部署职责，双人直接问答可以从路径 A 独立进入。[工作区](../src/workspaces.py) · [部署](deployment.md) · [订阅运维](c2-operations.md)

## 五、现有架构的依赖方向

| 入口动作 | 实际经过的核心 | 重构时容易误判的地方 |
| --- | --- | --- |
| 普通发信 | 空间桥接器或 HTTP MCP → 身份核验 → `MessageStore` → 项目请求和投递表 | 发信本身可以没有任务。请求有固定成员、请求键、上下文版本和收据语义，改造时需要明确哪些保证要保留。 |
| 普通读回信 | `WorkflowStore.read_replies` → 消息与回复表 → 左连接依赖路由和任务依赖 → 写提问方阅读记录 | 无任务数据时可以答复，读路径仍引用任务子系统表。 |
| 成员发现与上下文 | `list_members` 直接读成员目录；`read_capabilities`、`read_context` 从共享服务的基础快照再作筛选和投影 | “找一个人”和“了解项目正在发生什么”已有完全不同的读取成本和数据范围。 |
| 会话提示 | `checkpoint` 返回记录、摘要、策略；摘要装配问题、约定、交接、依赖等。任务绑定决定是否附加任务规则。 | 提示词变短只改变模型收到的规则，后台摘要装配仍包含工作流概念。 |
| 原生轻量接入 | 后端注册完整 MCP 工具 → 空间桥接器获取目录 → 在线或缓存路径筛选 → 调用处再限制 | 8 个可见工具描述的是新客户端的体验。服务端启动仍初始化任务、依赖、GitHub、约定和团队工作流；旧连接还可主动调用它们。 |

源码入口为[共享服务组合](../src/coordination.py)、[消息存储](../src/messages.py)、[答复查询](../src/workflow.py)、[检查点摘要](../src/checkpoints.py)、[工具注册](../src/mcp_service.py)和[桥接筛选](../src/space_bridge.py)。

## 七、哪些结论有真实使用证据

| 问题 | 当前可支持的结论 |
| --- | --- |
| 两个没有任务卡的成员，能否通过新入口完成问答？ | 当前基线有两个独立 stdio 客户端和 HTTP MCP 的端到端测试，验证寻址、发送、答复和回读。提问时机与内容由测试给定。[stdio 用例](../tests/test_space_bridge.py) · [HTTP 用例](../tests/test_mcp.py) |
| 真实 agent 是否曾经跨工具、跨机器交换信息？ | 有。旧版有 Windows 单机真实 Claude/Codex 闭环；后续 P0 记录有 Windows ↔ Linux、实际中继、原生文件问答、重连，以及特定配置的唤醒或待命。两台设备由同一维护者控制；这些结果有明确版本和拓扑，不能替代新轻量入口的独立团队验收。[单机记录](solo-acceptance-2026-10-29.md) · [后续跨设备记录](release-1.0-p0-acceptance.md) |
| 外部集成做到哪一步？ | GitHub App 的只读授权、真实事件、检查和撤权恢复有专用测试仓库记录；可写交付和生产合并需要单独证据。Stripe 有本地签名、传输与恢复测试，既有验收记录未报告真实支付闭环。[GitHub 记录](release-1.0-p0-acceptance.md) · [计费记录](commercial-c2-report.md) |
| 平台能否让普通团队少返工，尤其是避免写两份首页？ | 目前没有这个结论。已有评测会区分正确路由、显式读答、产物变化和人工提醒；原生配对基线尚未完成，DSH 云沙箱也有开放门槛。当前四个针对性回归覆盖了无卡传话、新鲜路径冲突阻塞、过期观察放行；没有覆盖跨路径的功能重复。[原生评测状态](foundation-1-native-acceptance.md) · [沙箱状态](dsh-sandbox-implementation-status.md) |

据此，后续重构最值得检验的产品价值可以说得很具体：**能否在两份实现分叉前让队员的 agent 发现彼此，在发现交集后直接核实，并让后来的会话沿用团队已经选定的实现。** 前两项之间有一段已可复用的通信、身份、送达与恢复能力；第一项的主动发现和第三项的按需继承仍缺普通团队环境下的验证。这是后续设计的依据，不是本次盘点已实现的功能。
