## 现有依据

- 已有按房间隔离的身份、任务、消息、约定、网页和 authenticated MCP。
- 现已增加独立账号、团队与多项目入口；项目 agent 令牌保留，C2 可选 cloud 订阅已实现，真实提供方尚未验收。

## 三种商业模式

| 模式 | 收费价值 | 开源与部署边界 | 主要代价 |
| --- | --- | --- | --- |
| 完整开源 + 官方托管（建议） | 托管、升级、备份、服务支持与企业实施 | 核心功能完整自托管；保持 MIT，不依赖官方许可服务器 | 需要证明官方服务的便利性与稳定性 |
| 开源基础版 + 企业扩展 | 企业功能和支持 | 需要明确每项功能的源码、许可及发行边界 | 容易增加双版本维护和用户理解成本 |
| 优先付费私有部署 | 部署、集成、迁移、培训和维护 | 客户使用开源代码，在自己的环境运行 | 收入较依赖交付服务，需要较多人工投入 |

首版支付平台已选择海外 Stripe，订阅为固定月付 Team；金额来自真实配置 Price，四项 Free / Team 容量由运营方明确配置，无预设售价或免费额度，不增加未验收企业能力承诺。不代理用户模型请求，也不将模型 token 消耗作为现有协作服务的计费依据。

## 建议的阶段划分

### C1：产品与身份基础

引入账号、团队工作区、多个项目和团队成员管理，让同一个用户能切换项目。保留现有项目级 agent 令牌及人工决定边界。历史房间、成员、消息、凭据通过附加迁移保留，不能通过自动认领身份将旧房间交给任意新账号。

登录方案在实施前明确：官方托管可选开发者 OAuth；私有部署需有不依赖官方云端的登录方式。账号恢复、成员撤销、会话失效和权限测试必须与登录一起设计。

网页增加产品入口、团队 / 项目切换和设置；保留现有自动分列看板。所有状态仍来自服务端，不用演示数据伪装订阅、使用量或连接状态。

### C2：官方托管订阅

已按团队账单实现单个固定月付 Team；活跃团队账号成员和绑定项目是容量边界，pending 邀请和历史项目协作者不会自动计费。托管模式的 Free / Team 限制在服务端事务执行，降级保留已有协作数据。完整 MIT 私有部署核心协作不依赖付款、云端密钥或联网许可检查；无 billing 配置的 cloud 也保持 Unlimited。

支付平台通过独立适配器接入；只以经过验证的服务端支付事件更新订阅，不能根据浏览器回跳宣告付款成功。覆盖事件重复、乱序、退款或失效、套餐变更及失败恢复。未配置真实支付平台时明确显示未启用，不能显示已支付或假结账按钮。

### C3：部署与运营验收

分别验证官方托管与私有部署：身份隔离、项目权限、数据迁移、备份恢复、实例升级以及原生 agent 闭环。明确收费页面的已交付能力，企业服务只承诺经过验收的项目。

商业模式、C1/C2 范围与分阶段计划已确认；源码、测试和维护文档继续分阶段提交 Git，所有凭据及原始数据留在忽略目录。

## 首版成功标准

- 同一账号能够进入有权限的多个项目；无权限团队与项目不可见。
- 管理员可以邀请和移出成员，被移出成员的网页会话与 agent 凭据不能继续访问该项目。
- 既有房间、任务、消息、约定和有效凭据可迁移，原数据库与证据保留。
- 官方托管具有明确且真实的订阅状态；私有部署核心功能不需要官方账号或付款才能使用。
- 部署文档能够分别指导两种模式，测试不把自托管可用等同于商业云端已经上线。
