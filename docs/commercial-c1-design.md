# C1：账号、团队与多项目设计

日期：2026-10-11。商业模式已确认：完整 MIT 开源 + 官方托管收费。此设计已获批准并实现为 `0.3.0rc1` 候选版；最新验收与外部验证边界见 [C1 报告](commercial-c1-report.md)。

## 本阶段产品行为

用户登录账号后进入团队，团队下有多个项目；项目内继续使用现有自动任务看板、技术请求、约定与个人 agent 接入。新增团队 / 项目切换和成员设置，不另做开发启动器。

私有部署使用本地账号密码，密码使用带独立盐的 scrypt 哈希；网页账号会话采用可撤销的 HttpOnly cookie。官方托管提供 GitHub OAuth 登录适配；未配置 OAuth 时界面明确提示该入口不可用，不展示虚假的成功状态。两种登录身份映射到统一账号与团队权限，不要求私有部署连接 GitHub 或官方云端。

已有房间网页令牌仍可用于旧入口。历史房间只能由持有当前有效 owner 网页凭据的人绑定进团队；不能因为新用户的名字、邮箱或仓库地址相同而自动取得旧数据。

## 数据与权限

- 新增账号、账号会话、OAuth 登录状态、团队、团队成员及团队项目关联；使用附加数据库迁移，保留已有表、原文件和凭据。
- 团队角色为 owner / admin / member。Owner 管理团队管理员；owner / admin 管理项目与邀请、移出普通成员；member 查看并参与被授予的项目。
- 项目权限和团队权限分别检查，任意客户端传入的团队 / 项目 ID 都不能直接成为授权依据。
- 团队账号与现有项目成员建立明确映射。账号登录不自动获得每个项目的权限；MCP 使用项目个人 agent 令牌，不能执行团队或订阅管理。
- 成员退出或被移出时，相关项目访问权限、网页访问凭据及 agent 凭据一并失效；最后一个 owner 不能被移出或降权。
- 登录 cookie 的有效期、退出与撤销由服务端决定；跨站写操作检查 Origin 和防伪凭据，公网 cookie 使用 Secure。密码、会话和 OAuth 临时令牌不出现在普通响应或日志中。

## 私有部署

保留当前 Compose、Caddy、SQLite 持久卷及备份恢复。增加清楚的运行模式：self-hosted 与 cloud；私有部署不执行云端套餐限制，也不检查官方许可服务器。

管理员使用现有建房密钥初始化首个账号 / 团队，不设置默认密码。之后通过成员邀请加入。私有部署账号忘记密码时由有权限的管理员执行明确的重置流程；不冒充已发送邮件。官方托管 OAuth 配置和真实登录验收需要部署者提供应用注册配置，密钥通过环境或 secret 文件提供。

## 交付与边界

本阶段交付账号与权限基础、团队 / 项目入口、迁移与独立部署文档及真实权限回归。仍采用适合当前单实例的 SQLite；数据库横向扩容另行实施，不把多团队逻辑称为已支持高可用。

订阅、套餐额度、支付、发票、企业 SSO 和 SLA 属于后续阶段，不通过本阶段界面假装已启用。现有 Codex 原生协作取消仍需独立解决，不能因为增加登录就标记闭环成功。

## 验收

1. 两个账号、两个团队及多个项目的隔离；越权路径、伪造 ID 与 agent 越权均被拒绝。
2. 登录、退出、过期、邀请兑换和被移出后的网页 / MCP 失效。
3. owner 权限保护；管理员不能移出或降权 owner。
4. 旧库附加迁移，旧 token 兼容，以及绑定旧房间必须提供有效 owner 凭据。
5. OAuth 状态一次性消费、回跳校验与失败处理；未配置时关闭入口，真实供应商登录另行记录。
6. 私有部署无官方联网依赖，备份恢复及已存在数据保持可用。
