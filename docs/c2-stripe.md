# C2 Stripe adapter and coordinator contract

This stage implements server-side billing configuration, authenticated raw-byte webhook ingestion, bounded Stripe HTTPS access, durable owner operations and canonical subscription reconciliation. It has no HTTP routes, billing UI or real payment evidence. All provider tests use transport fixtures; all coordinator tests use real retained SQLite databases under ignored `.local/c2-stripe-tests/`. The user has no Stripe account for this phase. Production account onboarding, a real monthly Price, webhook endpoint registration and external test-mode delivery remain release acceptance gaps. C3 remains paused.

## Modules and startup

`billing_config.py` parses configuration. `stripe_billing.py` owns transport, signatures and provider object identity/mode checks. `stripe_snapshot.py` verifies current subscription, invoice/payment relationships and risk. `billing_operations.py` persists outbound customer/portal keys. `billing_checkout.py` resolves claimed canonical Checkout creation/recovery/expiry. `billing_service.py` coordinates authorization, domain claims and provider I/O. The narrow additive domain option `BillingStore.reserve_checkout(team_id, *, lease_seconds=60, refresh=False, existing_only=False)` returns `None` for `existing_only=True` when no unresolved attempt exists inside its writer transaction; cleanup cannot accidentally create an attempt after another process confirms one. Other domain behavior follows [c2-domain.md](c2-domain.md).

```python
load_billing_config(deployment_mode: str, env=None) -> BillingConfig
# BillingConfig: enabled, catalog, secret_key, webhook_secret
# Both secrets are excluded from repr.

StripeClient(secret_key, mode, *, transport=None, timeout=5, max_pages=4,
             operation_seconds=45, max_requests=64)
BillingService(store, client, webhook_secret, canonical_origin)
```

Use deployment mode exactly `cloud` or `self-hosted`. Complete absence of all billing environment variables disables cloud billing. Once any billing variable is present, all eight logical values below are required; partial configuration, zero/invalid caps, unsupported modes and wrong credential prefixes fail startup. Four caps are positive integers at most 1,000,000,000; Team caps must cover Free caps. Configuration contains a Price ID, never a copied/embedded advertised monetary amount.

| Environment variable | Required meaning |
| --- | --- |
| `CREWMESH_BILLING_MODE` | Exactly `test` or `live` |
| `CREWMESH_STRIPE_SECRET_KEY` or `CREWMESH_STRIPE_SECRET_KEY_FILE` | Exactly one source; corresponding `sk_test_` or `sk_live_` key |
| `CREWMESH_STRIPE_WEBHOOK_SECRET` or `CREWMESH_STRIPE_WEBHOOK_SECRET_FILE` | Exactly one source; `whsec_` signing secret |
| `CREWMESH_TEAM_MONTHLY_PRICE_ID` | Configured Stripe `price_` identifier |
| `CREWMESH_FREE_MEMBERS` | Free active member cap |
| `CREWMESH_FREE_PROJECTS` | Free project cap |
| `CREWMESH_TEAM_MEMBERS` | Team active member cap |
| `CREWMESH_TEAM_PROJECTS` | Team project cap |

Secret files are read as ASCII with a 4096-byte bound and optional trailing CR/LF. Embedded whitespace, excessive length, absent/duplicate sources and inaccessible files fail with safe messages. Do not commit actual keys, secret files, machine configuration or raw provider data. Fixture secret strings are explicitly nonfunctional.

Self-hosted returns disabled before reading credentials or secret files. Construct `BillingService(disabled_store, None, None, None)` for unlimited self-hosted or unconfigured cloud summaries; no provider client or additional outbound ledger is needed. Each process must still construct its configured `BillingStore` to install the transactional workspace capacity hook. Enabled service requires a matching client mode, signing secret and server-configured canonical HTTPS origin. It reuses `config.public_origin`, including valid custom HTTPS ports. The origin is never request-controlled.

Startup validates local syntax and completeness without calling Stripe. Enabled startup therefore does not imply the Price is valid. `summary` retrieves the actual Price lazily, and `checkout` verifies it before any customer/Checkout mutation. Verification requires an active Price in the exact provider mode, fixed positive integer `unit_amount`, lowercase currency, recurring monthly interval, interval count exactly one, `licensed` usage, `per_unit` billing scheme, no `transform_quantity` and exactly one subscription quantity. Unsupported/tiered/metered/custom/zero/transformed prices cannot enable checkout. Any nonnull transformation is rejected because Stripe applies [quantity transformation](https://docs.stripe.com/billing/subscriptions/quantities#quantity-transformation) before calculating the charge; a displayed positive unit amount alone would not prove a positive flat charge for quantity one.

The displayed amount/currency are the Price's base values. A valid Price may contain alternate `currency_options`, but Checkout creation always sends the verified base `currency` and `adaptive_pricing[enabled]=false`. Stripe documents [server currency override](https://docs.stripe.com/payments/checkout/localize-prices/manual-currency-prices?payment-ui=stripe-hosted) for manual localization and [the explicit Adaptive Pricing setting](https://docs.stripe.com/api/checkout/sessions/create). Dashboard localization must not turn an advertised base-currency subscription into a charged alternate-currency invoice that canonical reconciliation rejects. `StripeClient.create_checkout(customer, price, key, attempt_id, origin, *, currency=None)` preserves its old signature: omitting currency verifies the configured Price and performs the GET/POST under the same operation budget and owner callback. The coordinator supplies its already verified base currency. Canonical Checkout currency must also match the retrieved configured Price before a hosted URL can be returned, recovered or expired. Existing alternate-currency sessions fail closed; this phase does not convert or adopt them.

## Public account methods

```python
summary(session_token, team_id) -> dict
checkout(session_token, team_id) -> dict
portal(session_token, team_id) -> dict
sync(session_token, team_id) -> dict
```

`summary` accepts any currently active team member and adds `price={amount, currency, interval}`, `price_error` (safe code or `None`) and `checkout_available` to the domain summary. `amount` is Stripe's actual minor-unit amount; formatting must respect Stripe currency units. `interval` is `month`. An unavailable or invalid Price gives `price=None` and disables checkout; it preserves the prior verified subscription and its entitlement. Membership is resolved again after Price I/O, so removed members cannot receive stale team data and demoted owners lose `can_manage`.

The other methods require the current owner. Authorization is rechecked before every provider request, after connection/DNS delay immediately before the physical HTTPS request, and before returning any redirect. Owner demotion during customer/Price/Checkout/portal work stops subsequent transport and suppresses the old owner's redirect. All network work runs outside SQLite writer transactions. A caller can pass only session and team ID; provider customer, Price, quantity, subscription and redirect values come from server bindings/catalog/origin.

`checkout` returns `{kind: 'checkout', url: HTTPS_URL}` for a verified open hosted session. Existing nonterminal subscriptions return `{kind: 'portal', url: HTTPS_URL}` after resolving any competing Checkout. A provider-confirmed expired session returns `{kind: 'expired', url: None}`; a subsequent owner request may reserve a new attempt. Complete sessions are reconciled and return the portal. Open unresolved sessions are refreshed even when a subscription snapshot arrives first; current subscriptions never cause a second Checkout create. Uncertain creates with an already current subscription require recovery lookup and fail closed if absent. Complete Checkout alone never grants Team.

Checkout line items are fetched canonically and must contain exactly the configured Price and quantity one. The session must be subscription mode, bound customer, configured base currency, stable server attempt reference and exact `origin/#billing-return` / `origin/#billing` URLs. Returned hosted URLs permit only HTTPS with exact appropriate host (`checkout.stripe.com` or `billing.stripe.com`), no credentials, raw backslashes, whitespace/controls or nondefault port, and at most 4096 characters. Stripe's [official Checkout response](https://docs.stripe.com/api/checkout/sessions/create) includes an opaque `#fidkd...` fragment: only exact `checkout.stripe.com` URLs may preserve this fragment unchanged, including durable domain storage and retry. Portal URLs reject every literal `#`, including an empty fragment delimiter; raw-string checks agree with the browser validator. Stored Checkout URLs also reject raw backslashes and other-host fragment delimiters. Store-generated keys exist before every write.

`sync` returns the authorized domain summary after canonical reconciliation; it creates/recover-binds the server-owned customer if necessary. It does not accept a paid status or arbitrary provider ID. Call `summary` when verified current Price display is also required. Domain access/conflict exceptions retain their credential-free messages. `StripeError` exposes only `.code` and that same short string; do not log raw transport exception/provider bodies.

## Durable operations and uncertainty

The additive `billing_outbound_operations` table has `operation_id` primary key, team foreign key, purpose (`customer`/`portal`), globally unique `idempotency_key`, `created_at`, state (`pending`/`complete`) and minimal `provider_id`. A partial unique index permits one pending operation per team/purpose. No raw bodies, card details, redirect secrets or credentials are stored. Customer creation uses the existing domain's stable random `customer_key` and team ID as server metadata, with identical parameters/key across processes. Customer operation keys never rotate, even when another process finishes binding between an unbound read and reserve. Portal calls reuse an uncertain pending key; after confirmed success another explicit portal request may create a new operation.

Checkout uses domain `reserve_checkout` before the remote call. Local lease expiry never rotates its key or proves expiry. A known session is retrieved canonically; an unknown create within the provider retention window retries the same persisted key. At age **24 hours or greater**, no unknown customer/Checkout create is reissued: a complete bounded canonical lookup must recover exactly one matching server key/reference and customer, otherwise the operation stays uncertain and fails closed. [Stripe retains keys for at least 24 hours](https://docs.stripe.com/api/idempotent_requests).

When a canonical nonterminal subscription exists, owner checkout/portal/sync, worker and administrator reconciliation claim only the existing unresolved attempt. A live competing lease reports `checkout_busy`; it never bypasses cleanup to return a portal or old Checkout URL. A verified open session is [expired remotely](https://docs.stripe.com/api/checkout/sessions/expire) with stable key `expire_` plus its persisted creation key, distinct from creation and unchanged across retry/restart. Expiry may be retried after 24 hours because it targets the same immutable session, cannot create a subscription and is resolved canonically if already terminal. Responses must retain session ID, customer, mode, attempt reference, configured Price/quantity and fixed redirects. Expiry timeout/rejection triggers canonical retrieval; only verified expired or matching completed state resolves it. A completed session for a different subscription reports `checkout_reconcile_required` and requires further canonical reconciliation; no portal or paid snapshot applies from that mismatch. Failed expiry leaves the attempt/key durable and the event pending. Cleanup runs before final generation-guarded snapshot application/processed marking. The domain's unleased complete confirmation cooldown can finish through a matching snapshot without competing with its own lease.

Customer recovery currently lists at most four pages of 100 customers (400 total). Checkout recovery lists at most 400 sessions for the bound customer. `has_more` beyond the bound, empty intermediate pages, repeated object IDs, zero matches and ambiguous matches fail closed. A larger account may require operator reconciliation tooling before automatic recovery succeeds. Search-based recovery is a future scalability improvement; eventual consistency must never justify blindly recreating an uncertain old operation.

Portal has no canonical session retrieval API. An uncertain portal create at age 24 hours cannot safely reuse a potentially forgotten key and reports `uncertain_portal`. This phase has no command to resolve that ledger state; operator tooling must verify/resolve it deliberately. Do not delete ledger rows, reset timestamps, fabricate snapshots, change keys or bind arbitrary customer IDs as a workaround. The retained state allows investigation. No manual paid setter exists.

## Raw webhooks and worker/admin methods

```python
ingest_webhook(raw: bytes, signature: str) -> bool
process_next() -> bool
reconcile_team(team_id) -> bool  # TRUSTED ADMIN/WORKER ONLY
```

The HTTP implementer must pass the original body bytes, require exactly one signature header and acknowledge only after durable ingestion succeeds. Authentication uses HMAC-SHA256 over the original decimal timestamp, a dot and the original raw body. Exactly one valid timestamp is required; absolute past/future tolerance is 300 seconds. Multiple `v1` signatures support secret rotation; comparison uses `hmac.compare_digest`. Duplicate timestamps, malformed fields, invalid hex signatures, unsupported mode, malformed/duplicate-key JSON, invalid typed IDs and numeric substitutes for booleans fail before any job is acknowledged. The verifier authenticates bytes before parsing JSON. Request size is bounded at 1 MiB.

Only event ID/type/object ID/mode are persisted. Incoming team/customer/subscription metadata is not authority. Duplicate identical IDs are deduplicated by `BillingStore`. Unsupported authenticated types are queued then safely ignored. Subscription, invoice, Checkout, charge refund, refund and dispute event families retrieve canonical objects and resolve a bound customer, then fetch current subscription/invoice state after acquiring a durable sync generation. A verified canonical standalone Charge with explicit `customer=None` (including one reached through a verified Refund/Dispute relationship) cannot match a team customer binding and is safely ignored without changing entitlement. Missing/malformed customer fields remain verification failures; subscription/invoice/Checkout customers must still be valid nonnull references. Event arrival timestamps do not order entitlements.

An event before local customer binding remains retryable. When remote creation succeeded and its process crashed before local binding, the worker can recover automatically after restart: the canonical customer's metadata must match a persisted random customer key/team and existing outbound customer operation, and a complete bounded lookup must prove exactly one canonical customer with that identity. Only then does it bind/complete the creation ledger and reconcile the event. A metadata team ID alone never authorizes binding. Unrelated canonical customers without local random-key provenance are ignored. Concurrent binding is re-read before treating a customer as unrelated.

`process_next` claims one durable job with a 120-second lease. It returns `True` for a processed/ignored job and `False` for no due work or a safely retried failure. Retry delays start at 30 seconds, double with a bounded exponent and cap at one hour; attempts persist across restart. Pre-sync lookup failures use `retry_job`, which cannot alter team state. After `start_sync`, failures use generation-guarded `fail_sync`; previous verified state survives. An old nonterminal subscription is first canonically reconciled to terminal before replacement, then a fresh generation fetches the new current objects. Event completion occurs only after the final valid snapshot applies. Old generations/expired claims cannot write snapshots or errors over newer results.

Run the worker off the async event loop; its provider calls are blocking but caller-bounded. The default provider operation budget is 45 seconds; surrounding SQLite calls (each connection has a 10-second busy timeout) and executor scheduling add time outside that budget. Shutdown must await the in-flight service work including those local database/scheduling delays, rather than treating 45 seconds as a bound on the entire `sync` or `process_next` method. The next HTTP stage must add application startup wiring, the worker lifecycle and bounded administrator reconciliation dispatch. `reconcile_team` accepts only an existing local team with a bound server customer and performs canonical reads plus expiry of a verified locally recorded competing session under a fresh operation budget; it cannot create customers/Checkouts, choose provider IDs or grant paid state. Enumerate work with `BillingStore.list_bound_teams(limit=..., after_team_id=...)`. Protect this method with an explicit admin/CLI boundary; it is not an account endpoint.

## Canonical paid evidence and provider bounds

The pinned API is `Stripe-Version: 2026-09-30.endive`; see [official references](c2-stripe-reference.md). Verify real endpoint registration uses that version. Customer/subscription/Price/invoice/payment/charge/dispute objects carry actual boolean mode matching the configured key. Current refunds omit `livemode`; their mode/customer/PaymentIntent evidence comes from the retrieved canonical related Charge. Dispute IDs use `du_`. The current [Charge object](https://docs.stripe.com/api/charges/object) has no legacy `invoice` field; invoice relationships are verified through [InvoicePayment](https://docs.stripe.com/api/invoice-payment/object)'s invoice and typed payment mapping. [Refund shape](https://docs.stripe.com/api/refunds/object), [Portal shape](https://docs.stripe.com/api/customer_portal/sessions/object).

A subscription must contain exactly one item/quantity one. Its paid period end comes from `items.data[0].current_period_end`, never subscription top-level or invoice accounting-period end. Its latest canonical invoice must belong to the same customer/mode and have `parent.type='subscription_details'` with matching nested subscription. Only active, unpaused, current paid invoices for the configured verified monthly Price can populate paid evidence. Past-due/unpaid/canceled/paused/pause_collection yields Free; period-end cancellation retains paid entitlement until its verified paid end.

Paid evidence also exhausts bounded canonical `StripeClient.invoice_lines(invoice_id)` (`GET /invoices/{id}/lines`). The [current Invoice Line Item](https://docs.stripe.com/api/invoice-line-item/object) must have `object=line_item`, `il_` ID, matching boolean mode/invoice/currency, `pricing.type=price_details` and the configured nested Price ID. Its `parent.type=subscription_item_details` must identify the same subscription and current item ID, with `proration=False`; its period start/end must exactly cover that item's current service period. Integer quantity is exactly one, and supplied `quantity_decimal` must be an exact decimal one because Stripe's integer quantity truncates decimals. A cheap/foreign Price or an old paid period cannot authorize the current period. The first fixed monthly scope supports exactly one positive full-period line; proration-only, multiple/extra invoice lines, absent or incomplete pagination and unsupported nested shapes fail closed. Payment evidence and paid-end derivation remain independently required.

For a current paid invoice, exhaust bounded `/invoice_payments?invoice=...` pagination and verify every paid record's invoice/currency. Follow `payment.type=payment_intent` to canonical `latest_charge`, or verify a direct Charge mapping. Every related intent/charge must have correct customer/mode/currency and successful fully captured payment evidence. Require unique charge IDs, exact per-payment allocation equal to intent received / charge captured amount, and total allocations equal to invoice `amount_paid`. Shared/ambiguous allocations and external `payment_record` types fail verification. This deliberately limits supported billing to fully attributable card/charge payments; credits, zero-total invoices, shared intents and externally recorded payments cannot newly grant Team.

Aggregate refunds only across those current invoice charges. A partial invoice refund preserves Team; aggregate full invoice refund holds it. Any unresolved or lost current-charge dispute holds it; canonical `won`/`warning_closed` clears that hold. Historical refunds/disputes do not freeze a new paid period. Risk is recomputed on every canonical fetch; incoming obsolete risk events cannot permanently freeze a team. Missing pages, payments or dispute evidence cannot create paid entitlement. Failed assessment preserves the previous verified snapshot without granting a new period.

Production transport uses only stdlib TLS to fixed `https://api.stripe.com/v1/` endpoints; it rejects redirects and reads at most 1 MiB. Defaults: five seconds per request, four list pages, 64 total requests and a 45-second provider operation budget; the client supports bounded explicit overrides. A process-wide 16-slot semaphore bounds physical HTTPS workers. DNS/header/body delays cannot hold the caller beyond its deadline: physical work runs in daemon threads, timed-out results cannot return to or mutate the caller, and slots remain held until actual physical completion. Saturation reports `provider_busy` without spawning more threads. Each response and connection is closed, including detached sockets after `Connection: close`. A physical call may complete remotely after the local timeout; it remains an **uncertain persisted-key operation**, never justification for a new key. If DNS finishes after the physical request deadline, the helper refuses to issue the delayed request. Owner authorization is also rechecked after connecting and immediately before sending.

## Validation

Coverage includes signature bytes/time/duplicates/mode, safe errors, invalid actual prices, response caps/redirects, detached socket cleanup and strict caller deadlines/saturation; retained SQLite keys across reconstruction/fresh processes and binding races; both snapshot/Checkout orders; provider-confirmed expiry; old subscription replacement; current/historical/partial/full refunds, direct/multiple payments, pagination bounds, dispute reopen/close; owner demotion/removal during provider work; prebinding event recovery without owner action; event dedup/out-of-order/restart retries and stale generation rejection; unlimited self-hosted no-provider behavior.
