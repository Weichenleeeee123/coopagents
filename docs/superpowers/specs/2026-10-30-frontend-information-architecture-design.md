# 前端信息架构重整

日期：2026-10-30。

状态：针对用户反馈的结构修订提案，待确认。本提案承接已批准的轻量黑白视觉，但重新划分页面职责；尚未修改产品代码。

## 问题

用户反馈：各界面条理不清，项目和功能混乱，不够直观，所有内容像堆在一起。

此前改版解决了边框、字体和响应式，却没有建立稳定的信息架构。通过折叠和内部滚动减少页面长度，无法让用户理解信息归属。

源码审阅依据：`index.html` 的项目导航、账号中心与 `view-overview`，`accounts.js` 的四个账号视图，`app.js` 的页面与渲染入口，以及 `board.html` 的长页结构。

具体原因：

- 导航层级混用：“团队现场”是汇总页，“任务”和“请求”是工作对象，“仓库接入”是配置操作。
- 项目级的成员与 agent、上下文、交付、活动、资产没有各自明确的页面，集中在团队现场。
- 团队成员管理、项目协作者、agent 会话没有清楚区分，账号中心与项目页看起来像两个互相切换的产品。
- 项目选择藏在团队/项目两个选择器里，当前项目和返回项目列表的位置不够直观。
- 共享上下文将任务、会话、活动再次投影成连续记录，容易被理解为另一份重复的活动日志。
- 完整证据与技术诊断提前占用普通页面，常用信息缺少摘要和明确的详情入口。
- 只读看板仍将所有对象连续排列；外观与账号版相似，浏览结构却不同。

## 设计原则

1. 明确当前位置：当前团队、当前项目和当前页面分别可见，切换项目不经过设置页。
2. 每个工作对象有一个主要操作入口，其他页面仅展示与当前对象相关的摘要和链接。
3. 概览负责判断和进入，功能页负责查找和操作，详情负责关联信息，设置负责配置。
4. 界面分组不规定工作先后顺序。任务、请求、上下文和交付可独立使用。
5. 人类页面按工作对象组织；底层 MCP 能力保持可组合，不将工具列表直接映射成页面区块。
6. 数据、权限、来源和状态含义保留，简化的是默认展示和导航。

## 方案比较

| 方案 | 做法 | 判断 |
| --- | --- | --- |
| 按工作对象组织，推荐 | 项目内建立概览、任务、协作、上下文、交付、成员六个入口 | 归属稳定，核心能力容易找到，适合现有产品范围 |
| 单页加更多折叠 | 继续把完整模块放在团队现场 | 成本低，但用户仍需知道内容藏在哪里，不能解决本次反馈 |
| 固定流程分步 | 按接入、分工、沟通、交付、验收组织页面 | 与能力优先、不强制团队流程的定位冲突，不采用 |

## 页面骨架

```text
团队 / 项目选择器
  当前团队
  当前项目名称 + 仓库简写
  切换项目 / 全部项目

当前项目
  概览
  任务
  协作
  共享上下文
  交付
  成员与 agent

项目设置
个人账号菜单
```

项目选择器提供当前可访问项目列表；团队管理、团队角色和套餐收进团队菜单，个人密码与退出收进个人菜单。无账号的本机空间不展示团队或账号菜单。

## 页面职责

| 页面 | 用户问题 | 默认内容 | 详情或次级入口 |
| --- | --- | --- | --- |
| 概览 | 这个项目现在怎么样，有什么需要关注？ | 项目与仓库、少量关键状态、待处理事项、最近几条重要变化 | 进入相关任务、请求、交付；完整活动历史 |
| 任务 | 谁在做什么，当前进展如何？ | 标题、负责人、状态、最新进展的任务集合与筛选 | 任务详情中的依赖、相关请求、交付引用；范围交叠 |
| 协作 | 有什么问题需要谁回应？ | 请求列表，突出对象、最新回复与处理状态 | 请求详情、关联任务、依赖答复与处理记录 |
| 共享上下文 | 团队已经共享了什么，可引用什么？ | 约定、共享文件与查询入口；各类内容用页内标签切换 | 约定版本/审批、文件来源/下载、跨对象共享记录查询 |
| 交付 | 哪些分支、commit、PR、Release 对应哪些工作？ | 按交付对象组织的列表、关联任务、来源与状态 | 对象详情、关联建议与授权确认、同步信息 |
| 成员与 agent | 队友有哪些 agent，能做什么？ | 项目成员及其 agent、工具、关联工作与最近状态 | 单个 agent 的能力/连接证据、完整 Harness 矩阵、接入自己的 agent |
| 项目设置 | 如何连接、授权和排查？ | 仓库绑定、本地接入、GitHub 同步配置，按用途切换 | 高级诊断、凭据、迁移等原有授权操作 |

共享上下文的页内标签为“约定”“文件”“共享记录”。默认明确展示共享内容，不直接将所有内部记录平铺。共享记录保留统一查询 API 的所有现有能力；本轮不新增自由笔记、全文索引或后台知识库。

任务保留既有状态与分列含义，不建立强制验收流程。是否增加列表/看板切换属于展示方式选择，实施计划中明确，不能借此改变状态机。

## 去重与关联

- 概览不嵌入完整的成员列表、上下文查询、交付图、活动流或文件上传表单。
- 项目成员页拥有成员与会话发现；任务页只显示负责人摘要，任务详情可跳到该成员或 agent。
- 公共约定的主要入口属于共享上下文；请求里保留相关约定链接，避免两个完整约定列表。
- 任务详情只展示该任务相关的请求、依赖和交付。项目级日志、仓库绑定表单和全量能力矩阵不放进详情。
- 交付页拥有项目级交付查找和关联操作；任务详情展示同一事实的相关子集，不产生另一套关联状态。
- 项目活动作为概览的次级视图，可完整查询；默认概览仅呈现有限条目，避免依靠嵌套滚动控制长度。
- 能力验证、凭据、传输连接、模型处理分别呈现。细节后置不能让“最近登记”被误认为“在线可唤醒”。

## 页面内部结构

各功能页沿用同一阅读顺序：页标题与当前范围、常用筛选和主要动作、结果集合、对象详情。

列表默认显示可供判断的内容，例如请求的标题/内容摘要、发送人与接收人、状态和最后回复。机器 ID、完整来源串、版本证据与审计记录放在详情内。不能用技术字段替代成员名称或工作标题。

一个页面只有一个主内容区。页内标签用于同一能力的不同视图，折叠用于当前对象的次要细节；二者不用于隐藏原本应该独立的功能页。

页面使用稳定地址恢复项目内当前视图，刷新、返回、任务链接和对象跳转可预测。切换项目清理原项目的筛选、对象详情与私密展示；切换页面保留本页合理的浏览状态。

## 只读与手机

只读看板复用相同的项目页面分组和导航，只保留查看权限。不得为复用账号界面向只读会话开放管理接口。

手机首屏优先展示当前项目、当前页面和页面内容，导航提供可发现的菜单入口。不能让一整块桌面侧栏、统计和筛选占满首屏，也不能依赖长串被裁切的标签作为唯一导航。

## 验收标准

视觉和溢出检查保留，但不足以证明结构清晰。本轮还需要验证以下查找任务：

1. 从一个项目切到另一个项目，始终看清当前项目，不误入团队或账号设置。
2. 找到队友的某个 agent，查看其工具与关联工作，必要时展开能力证据。
3. 找到当前生效的约定及其来源，区分待审新版本。
4. 找到一项需要回应的请求，理解发送人、接收人与最新答复。
5. 从任务找到关联 PR，从 PR 回到相关任务，保持当前位置可理解。
6. 找到共享文件、完整活动和连接诊断，各自入口有明确归属。
7. 通过只读入口完成同类查找，不能执行管理动作。

以上常用目标应在进入项目后通过明确入口到达，不靠滚动遍历其他完整模块。检查正常、空数据、多成员/多 agent、大量任务/活动、未知/过期能力和手机场景。

## 实施顺序

1. 确认导航与页面归属，先做结构原型，使用包含真实复杂度的合成项目展示六个页面及来回跳转。
2. 按同一骨架迁移现有渲染和操作，调整账号/项目入口与只读导航；不新增后端工作流。
3. 完成跨对象跳转、刷新/返回、会话失效和权限回归，再进行桌面/手机浏览器验收。
4. 按阶段提交源码、测试和维护文档；保留全部历史文件、数据库和证据，不推送或发布。
