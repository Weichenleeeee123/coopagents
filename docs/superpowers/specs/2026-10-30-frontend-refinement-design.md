# Coopagents 前端简洁化设计

日期：2026-10-30。

状态：用户已确认 A「轻量黑白工作台」，按本设计分阶段实施。

## 目标

为跨电脑、跨 coding agent 的小团队提供简洁、优雅、适合反复使用的协作工作台。围绕已完成的 0.9.1–0.9.3 能力统一页面层级，让用户容易找到队友、当前工作、共享上下文和交付证据。

保留能力自由组合的产品方向。信息展示不引入强制操作顺序；登记、连接、送达、处理和已验证能力仍各自表达，合并与发布不代表任务验收。

## 现状依据

当前视觉基线是用户曾确认的黑白工业风，见 [黑白工业验收](../../frontend-monochrome-validation.md)。更早的森林绿与薄荷绿提案作为历史记录保留。

本轮检查了 `src/static/index.html`、`board.html`、`styles.css` 及现有页面渲染模块，发现：

- 黑色边框、2px 分隔线和偏移阴影同时出现，页面大部分元素都在争夺注意力。
- 36px 页标题、46px 摘要数字、重复的英文眉题与说明增加首屏负担。
- 共享上下文、能力发现、交付关联尚无专属组件样式，排版与旧页面不一致。
- 能力发现把姓名、会话数和多个会话直接放入原有双列成员网格，存在错误配列风险。
- 团队现场连续展示成员、能力、交叠、上下文、交付、活动和资产，页面过长，缺少清楚的章节边界。
- 共享上下文七项筛选全部展开，来源和引用等元数据与正文缺少视觉区分。
- 账号设置、接入和证据区域反复嵌套带框容器，主次不清。
- 字距和登录字号存在多处独立规则，需要随排版统一。

以上是源码审阅结论；浏览器实际效果及溢出情况在实施阶段验证。

## 方向选择

| 方向 | 呈现 | 取舍 |
| --- | --- | --- |
| A：轻量黑白工作台，推荐 | 延续近黑与白色，细分隔线、克制圆角、低噪声元数据；语义色只用于重要状态 | 延续已有品牌，覆盖现有全部页面，可在原生技术栈内完成 |
| B：全浅色工作台 | 浅色侧栏、白色内容，以排版和细线区分导航 | 整体更明亮，但改变既有深色导航识别，主次需要重新建立 |
| C：紧凑工具台 | 更小间距、更多表格和并排证据 | 浏览效率高，但信息压力更大，与本轮简洁优雅目标的契合度较低 |

建议采用 A。重点是提高阅读与操作的清晰度，同时延续此前选定的黑白品牌。

## 视觉基础

- 内容底色 `#F7F8FA`，主要表面白色，正文 `#202124`，次要文字 `#62666D`，边线 `#E3E5E8`，侧栏 `#202124`。实施时以浏览器计算对比度校正。
- 主操作保持近黑；成功、警告与失败可少量使用绿、琥珀、红，并配合明确文字。未知能力保持中性，不用成功色。
- 删除视觉上的硬偏移阴影；普通内容通过留白和细线组织。阴影只用于浮层和极轻的可交互反馈。
- 输入、按钮、任务和项目卡片圆角统一为 6–8px；页面章节不套浮动卡片，记录内部不再嵌套卡片。
- 页标题 26px，区块标题 18px，记录标题 15–16px，正文 14px，辅助文字 12–13px。摘要数字约 26px，使用等宽数字保证稳定。字距统一为 0，不使用随视口连续缩放的字体。
- 中文和英文使用本地清晰字体，技术引用采用等宽字体；不增加外部字体服务。
- 间距使用 4、8、12、16、24、32px。桌面侧栏约 232px，正文左右 24–32px。交互目标桌面至少 36–40px，手机至少 44px。
- 工具型按钮优先使用图标并提供可访问名称和悬浮提示；保存、邀请、创建等明确命令保留文字。保留品牌图标，不增加装饰性图形。

## 页面设计

### 全局框架与入口

账号中心、项目工作台、本机只读看板共用排版、控件和状态样式。精简重复眉题、口号、教学性说明和页脚；影响判断的权限、安全、状态来源和能力限制仍在相关操作旁呈现。

深色侧栏保留品牌、当前项目、导航及账号入口，选中项用克制的浅色背景标识。顶部只呈现当前位置、同步状态和刷新操作。

登录页改为简洁的品牌与表单入口，压缩宣传性大标题与装饰占位，让可用登录方式、错误和重试更清楚。初始化、邀请及旧凭据入口继续由现有部署条件控制。

### 任务看板与详情

把摘要改为紧凑统计行，搜索、状态、负责人和新建任务形成清晰的工具栏。延续现有自动分列及任务操作，减少卡片边框和元数据的视觉重量。

任务卡片突出标题、当前状态、负责人和最近进展；声明范围、时间与证据摘要放在次级位置。长路径允许换行，提交标识保持可辨认。

详情继续使用原生右侧 dialog，按概况、进展、交付、协作记录排列；以章节分隔，压缩重复标签。手机接近全屏，保留 Escape、焦点恢复和凭据关闭清除行为。

### 团队现场与能力发现

团队现场用清楚的区块标题与间距组织：需要关注、成员与能力、共享上下文、交付、活动与资产。范围交叠和 Git 交叠保持各自来源，放在次级位置。

成员工作现场和能力发现使用协调的列表结构，修正原有成员网格的错配。每个 agent 首先呈现 Harness、分支、任务与最近状态；详细能力证据和完整支持矩阵按需展开。

折叠内容保留来源、版本、平台、验证时间和状态。最近登记、检查点出现、连接、送达、模型处理均独立展示，未知项明确标注未知。

### 共享上下文、交付、活动与资产

共享上下文默认呈现搜索、任务与成员；范围、分支、交付类型和标识在高级筛选中保留。展开状态与输入不被同步刷新打断，查询分页与错误反馈继续可见。

上下文记录采用清晰的连续列表，标题和正文为主，来源、新鲜度、范围与引用为辅。待确认建议、生效约定、已过期证据可扫描区分。

交付关联以交付对象为标题，关联任务作为可点击引用，关联来源与远端同步状态分别呈现。确认和拒绝按钮仅在原有授权与待确认状态下出现。

活动使用时间线式列表；资产使用紧凑文件列表。长引用、摘要和文件名允许换行，完整证据仍可查看。

### 账号、请求、约定、仓库与账单

各页面沿用现有导航和行为，统一标题、表单、操作栏、错误、空状态和加载状态。团队设置与仓库接入使用无框章节，成员、项目、请求等重复条目才使用轻量记录表面。

请求强调问题与最新回复；约定突出当前生效版本和待审版本；仓库接入分别展示本地连接和 GitHub 同步状态；账单保留既有英文、权限与付款语义。

## 实施边界

沿用原生 HTML、CSS、JavaScript 与共同渲染模块。样式在现有组件规则中整理，避免追加一整套覆盖层。修改渲染结构时保留 DOM ID、事件接口、权限条件和会话失效保护。

本轮涉及静态资源与必要的界面回归，不改变 API、数据库、任务状态机及 Harness 支持判定，不新增工作流步骤。所有文件保留；旧文档与历史截图保留。

## 分阶段交付与验收

1. 确认本设计，补充实施计划并提交设计阶段文档。
2. 统一视觉基础与全局框架，覆盖登录、账号、工作台和只读页面，提交第一阶段。
3. 打磨看板、详情与三项新增能力的排版和信息层级，提交第二阶段；涉及折叠、筛选和刷新保护的行为补充对应回归。
4. 运行受影响网页回归、脚本语法检查及网页 HTTP 测试；以真实本机服务进行浏览器操作和截图验证，记录结论后提交验收阶段。

浏览器检查 1440、1280、768、390、320px：文档不横向溢出，允许看板与代码区域内部滚动，长姓名、路径与文件名不覆盖操作，弹窗、键盘焦点和手机导航可用。正文对比度至少 4.5:1，减少动态效果设置生效。

验证登录与账号各视图、看板搜索/筛选/详情、团队现场三项能力、技术请求、公共约定、仓库接入、只读看板，以及加载、空数据、失败、断线状态。真实服务与合成展示数据明确区分，不将页面验收解释为跨电脑或 Harness 真实验收。

本机数据库、脚本、截图与配置保存在独立 `.local/` 目录，不提交 Git。实施后保留本机预览服务并提供地址，不自动推送或发布。
