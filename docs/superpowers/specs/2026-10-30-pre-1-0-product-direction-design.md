# Coopagents 1.0 前产品方向

日期：2026-10-30。状态：产品范围与方向已确认；本文记录 1.0 前的能力深化、适配验收和产品化准备，不替代各阶段的实施计划与验收报告。

## 产品目标

让不同 harness、不同电脑上的 coding agent 围绕同一个项目共享协作上下文、发现彼此并理解可用能力，再把协作工作连接到可追溯的交付证据。Coopagents 提供可组合的能力，不要求团队采用固定的开工、沟通、交接或验收流程。

## 产品原则

- **能力优先于流程。** Agent 和成员按需要查询、分享和关联信息；产品不规定每个任务必须遵循同一套步骤。
- **共享信息有据可查。** 显示信息应能说明来源、适用范围、更新时间和新鲜度，并区分确认事实、明确报告、外部观测与待确认建议。
- **尊重原有工具和权限。** 团队继续使用自己的 harness、电脑、仓库与 Git 工作方式；Coopagents 不代替用户批准团队决策或执行交付操作。
- **保护私人会话。** 不读取或共享完整提示词、回复、隐藏推理、工具输入输出或私人会话记录。共享内容来自明确的协作操作、明确提交的信息或授权来源的结构化事实。
- **如实说明能力。** 连接、消息送达、模型读取和任务处理是不同状态。未实测的 harness、平台或 hook 能力保持 `unknown`，不宣传为已支持。

## 1.0 前的能力深化

### 0.9.1：深化共享上下文

把项目中已存在的任务、确认过的约定、依赖、明确分享的资产、协作活动和 Git 交付引用，做成 agent 与成员可以按需查询、引用和分享的项目上下文。

- 查询可按项目、任务、成员、分支或交付对象等有意义的范围进行，不强制先执行某个固定的“开工简报”步骤。
- 每条上下文提供其来源、时间、版本或目标对象、适用范围及新鲜度；外部状态不可用或过期时明确标示。
- 区分经成员确认的事实、agent 明确提交的进展、外部来源的只读观测和待确认建议。
- 共享上下文复用现有领域权限，并能从相关任务、活动或交付对象回溯；不得通过上下文功能旁路私人会话隐私边界。

### 0.9.2：成员与能力发现

让团队可以看到项目成员及其 agent 会话，理解“谁在使用什么工具、哪些能力可用、当前状态有多新”。成员和 agent 会话是不同对象；一个成员可以连接多个 agent。

- 展示已知的成员、agent/harness、工具版本、关联项目或仓库上下文，以及可用时的分支和最近活动。
- 展示 MCP、项目上下文、session lifecycle、native hook、idle wake 等按 harness、版本和平台记录的能力矩阵。
- 状态区分已验证支持、不支持、未知、当前不可用和证据过期；保留验证版本、平台、时间与限制。
- 清楚区分成员/会话登记、连接可用、最近出现、事件送达和 agent 实际处理，不能用在线指示暗示模型正在工作或可立即响应。
- 只展示完成协作所需的结构化信息，不展示私人会话内容、完整提示词或任意工具记录。

### 0.9.3：优化交付关联

分支、commit、PR 和 Release 的关联能力已经在现有设计与实现中；本阶段以此为基础完善产品体验和证据可追溯性，不另起一套交付模型。

- 从任务和项目视角清晰查看关联的 branch、commit、PR、Release，以及关系由谁或哪个授权来源建立。
- 可从交付对象反查相关任务，并呈现多对多关系、关联证据、状态来源、同步时间和陈旧/不可用状态。
- 对可能的关联继续明确标为建议；需要成员确认的关系不得静默升级为事实。
- PR 合并或 Release 发布只表示对应的 Git 交付事实，不自动关闭任务、不表示团队验收，也不替代成员确认。

责任转移不作为 1.0 前新增能力方向；团队仍可使用现有任务与消息能力，但本阶段不扩展为必须经过的交接工作流。

## Harness 适配与验收主线

能力深化之外，harness 适配与验收是 1.0 发布前的必做主线，与 0.9.1–0.9.3 并行推进。首批范围为 Claude Code、Codex、Cursor、OpenCode、Pi、Kimi Code 和 ZCode。

- 对每个 harness 验证官方支持范围内的 MCP 基础接入与协作闭环；配置必须安全、幂等并保留无关设置。
- 只有 harness 官方提供且经过真实验证的生命周期、hook、ACP 或唤醒能力，才在对应矩阵单元中标为支持。MCP 接入通过不代表 native hook 或自动唤醒通过。
- 按 harness、版本、操作系统和能力逐项记录证据与限制。Windows、macOS、Linux 的结论不得相互外推；无法真实运行的组合标注未验证。
- 真实 agent 闭环、双设备网络、重启恢复和 GitHub App 等发布门槛按[1.0 发布就绪计划](../../release-1.0-plan.md)执行；测试与报告不得以模拟成功替代所需的真实证据。

## 产品化与发布准备

产品化工作在能力深化和适配验收期间并行开展，目标是在公开发布前让用户理解产品、顺利开始使用，并能看到可信的实际效果。

1. **定位与宣传边界：** 强调不同 agent、不同电脑围绕同一项目协作。明确这是一层共享协作能力，不是强制团队工作流；不宣称完整私人会话共享或所有 harness 均支持自动唤醒。说明 P2P/自托管模式、网络条件和各组合的能力边界。
2. **首次使用体验：** 打磨安装、创建/加入空间、邀请、原生配置、连接诊断、能力状态与故障排查。诊断应指出实际问题及可采取的下一步，不把“命令已运行”误报为接入成功。
3. **真实公开演示：** 准备至少两台真实设备和两个不同 harness 的可复现演示，展示按需共享上下文、成员与能力发现、agent 之间直接协作，以及任务到 commit/PR 的交付证据。演示标明版本、网络路径和已知限制，不包含凭据或私人会话内容。
4. **发布材料：** 更新 README 与项目主页或官网入口、截图和短演示视频；发布支持矩阵、安全说明、已知限制和明确的试用入口。对外文案只使用有证据支持的功能与兼容性结论。

## 阶段顺序与 1.0 收口

| 阶段 | 重点 | 收口条件 |
| --- | --- | --- |
| 0.9.1 | 共享上下文 | 信息可按需查询，来源、范围和新鲜度清楚，隐私及权限边界保持有效 |
| 0.9.2 | 成员与能力发现 | 多成员、多 agent 的身份和能力矩阵可见，状态语义及验证证据明确 |
| 0.9.3 | 交付关联优化 | 现有关联可发现、可追溯，建议、观测和明确关系能区分 |
| 并行贯穿 0.9.x | Harness 适配与验证 | 七个目标 harness 的基础接入有逐组合证据；宣称支持的扩展能力和平台组合有独立验证 |
| 1.0 RC 前 | 产品化与发布准备 | 首次使用、公开演示、发布材料及能力/安全/限制说明完成；进入 RC 后按发布就绪计划冻结功能并收敛缺陷 |

阶段编号表示建议顺序，不要求对应能力被打包成不可组合的用户流程。若实施计划或真实验收暴露依赖，应在相应阶段文档中记录调整及理由。
