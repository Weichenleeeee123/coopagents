# Crewmesh 整体前端设计提案

日期：2026-10-11

状态：待用户确认；本文件是设计提案，尚未修改产品页面。

范围：登录、团队与项目、任务看板、团队现场、技术请求、公共约定、仓库接入、任务与凭据弹窗。

## 目标与现状

让用户进入后能迅速选择项目、找到需要协助的工作、判断交付证据，并清楚地完成当前操作。整体保持适合日常开发的工作台气质。

本轮依据当前 `src/static/`、账号与账单设计文档，以及仓库中保留的看板、C2 桌面和移动端截图进行审阅。截图是历史验收证据，不代表本轮已完成浏览器验收。

具体问题：

- `styles.css` 同时保留早期森林绿／米白规则和后续石墨灰／薄荷绿覆盖。项目卡片、表单、弹窗和账单面板的背景、圆角及字号不统一。
- 账号中心把项目选择、账单、建立团队、团队管理、改密和成员列表放在一个长页。日常入口和低频配置竞争注意力。
- 项目侧栏已有五个导航项，移动规则仍用四列网格；团队、项目、账号入口与其他侧栏信息进一步拉长首屏。
- 看板卡片的负责人、路径和时间为 9–11px，阅读负担大；新建按钮和整行「声明一项新工作」重复占位。
- 五列看板有明确最小宽度，需把横向滚动限定在看板内，并给窄屏用户明确的位置提示。
- 任务详情、请求、公共约定与 Git 证据采用长段落堆叠。关键状态与次要记录缺乏稳定的阅读顺序。

## 方向比较

| 方向 | 做法 | 取舍 |
| --- | --- | --- |
| A · 品牌延续与整体精修（推荐） | 石墨色导航、浅色内容、薄荷绿操作；统一所有页面的布局与组件 | 保留当前识别度，覆盖现有主要问题，实施范围可控 |
| B · 紧凑开发者工作台 | 减少留白、强化列表与表格、更多信息并排展示 | 适合重度用户；首次接入和移动端更需要额外引导 |
| C · 温暖的品牌工作室 | 回归米白和森林绿、放大衬线标题、强调品牌叙事 | 登录页更有表现力；任务与证据页面仍需另一套紧凑排版 |

建议采用 A，吸收 B 的信息层级：重点信息更清晰，而不是让所有内容都变得更密。

## 统一视觉系统

- 页面底色 `#F4F6F5`，内容表面 `#FFFFFF`，导航 `#17211D`，正文 `#202B25`，次要正文 `#58665D`，边线 `#DCE3DE`。
- 薄荷绿 `#8CE8BD` 用于主要操作及选中状态，文字为深绿；普通按钮使用白底描边。警告、受阻、成功分别采用琥珀、砖红和深绿，并始终配合文字说明。
- 登录大标题保留品牌气质；工作台页标题统一为 28–32px，区块标题 18–20px，正文 14px，辅助内容原则上不低于 12px。
- 品牌保留现有图标与 Crewmesh 字标。中文正文使用本地可用的清晰字体，路径、提交和配置使用等宽字体，不新增外部字体请求。
- 采用 4／8／12／16／24／32px 间距；控件圆角 8px，内容卡片 12px。层级主要通过间距、边线和表面区分，阴影用于浮层和轻微悬停反馈。
- 常用控件高度 40px，移动端交互目标至少 44px。所有交互有可见焦点；动效控制在约 120–180ms，并遵守减少动态效果的系统设置。
- 配色作为实施起点；浏览器验收检查普通文本至少 4.5:1 的对比度，必要时调整 token。

## 页面与布局

### 全局工作台

桌面统一账号中心与项目工作台的侧栏宽度、品牌区、间距和账号入口。项目工作台的顺序为品牌、团队／项目选择、项目导航、接入入口、当前身份。

内容区顶部仅保留当前位置、最近同步时间和刷新按钮；下一行是页标题、简短说明和主操作。看板使用可用宽度，表单与长文本限制阅读宽度。

```text
┌────────────────┬─────────────────────────────────────────────────┐
│ Crewmesh 同频  │ 团队 / 当前项目                 最后同步 · 刷新 │
│ 团队 · 项目    ├─────────────────────────────────────────────────┤
│                │ 任务看板                            ＋ 新建任务 │
│ 任务看板       │ 搜索任务              负责人筛选      任务数量 │
│ 团队现场       │                                                 │
│ 技术请求       │ 待认领   推进中   遇到阻塞   待验收   已合并   │
│ 公共约定       │ ┌────┐   ┌────┐   ┌────┐                         │
│ 仓库接入       │ │任务│   │任务│   │任务│                         │
│                │ └────┘   └────┘   └────┘                         │
│ 接入 agent     │                                                 │
│ 账号与团队     │                                                 │
└────────────────┴─────────────────────────────────────────────────┘
```

### 登录与首次使用

桌面保留品牌叙事和登录表单双栏。表单区明确呈现当前可用的入口：账号登录、首次初始化、邀请注册或 GitHub 登录，继续由部署配置决定。

旧项目凭据入口保留折叠展示；与会话和部署有关的说明放在对应入口附近，缩短无关说明占用的首屏。移动端先呈现精简品牌区与主要表单，装饰区域收起。错误显示在关联表单内，重试入口在需要时清楚出现。

### 团队与项目中心

使用「项目」「成员」「团队设置」「Plan & billing」四个账号中心视图，复用当前账号数据和表单。页内导航仅切换展示，不新增后端路由。

- 项目：项目卡片和进入项目是主内容；管理者可直接展开创建项目表单。无项目时给出符合当前角色的下一步。
- 成员：清晰展示身份、角色与管理操作；项目权限和凭据管理继续按成员折叠。移出／离开团队采用明确的危险操作样式。
- 团队设置：建立团队、接受邀请、管理者邀请成员、接管旧项目与本人改密按用途分组。
- Plan & billing：沿用英文及当前权限语义，纳入同一套卡片与控件样式；`#billing` 和 `#billing-return` 直接打开该视图，保留付款返回确认逻辑。

项目选择仍通过现有授权接口进入工作台。切换团队清除旧内容，默认回到项目视图；从账单返回的入口按原有 fragment 规则显示账单。团队角色仅影响已有操作的显示与可用性，不改变服务端授权。

### 任务看板与详情

保留五个工作阶段及现有自动分列规则。工具栏整合搜索、负责人和数量，新建任务通过一个主按钮展开现有表单；表单的三个字段和语义保持清晰。

卡片阅读顺序为任务编号、标题、最新进展、声明范围、负责人、更新时间。关联请求和 Git 摘要置于稳定的次要位置。颜色用于状态提示，避免整张卡片染色。无数据和筛选无结果使用不同文案，筛选无结果提供清除筛选入口。

桌面详情采用靠右的原生 dialog 面板，让看板仍作为背景；窄屏切为接近全屏。详情依次展示概况、最新进展、交付证据、关联请求、公共约定。较长配置、技术标识和历史记录按需展开。关闭、Escape 与焦点返回维持原生可访问行为。

### 团队现场、请求与约定

团队现场顶部用紧凑摘要呈现成员、任务和待解决请求。成员与正在推进的工作在主体展示，声明交叠和实际 Git 交叠各自作为明确区块，保留来源与时间。

技术请求突出问题、发送与接收成员、当前处理状态、最新回复；读取、处理、回应、解决仍分别记录。公共约定把当前版本、生效版本和审核动作集中展示，历史版本折叠保留。需要用户操作的位置使用一致的操作栏。

### 仓库接入与凭据

仓库页分为「共同仓库」「本地 agent 接入」「GitHub 交付同步」三个区块。每个区块呈现自己的状态与可用下一步，避免把本地接入和远端授权混成单一成功状态。

凭据对话框使用相同的标题、字段和按钮规则；安全说明靠近对应操作。保持凭据关闭即清除、显隐与复制行为以及现有权限条件。

## 响应式和反馈

- 1200px 及以上：侧栏约 232px，内容两侧 24–32px，看板五列最小约 208px；放不下时仅看板横向滚动。
- 768–1199px：侧栏约 208px，紧凑内容间距；表单根据可用空间改成两列或单列。
- 767px 及以下：精简顶部品牌区，团队／项目选择与账号操作可展开；五个项目入口使用可横向滚动的单行导航，当前入口清晰可见。看板卡列宽约为视口的 84%，露出相邻列并保留滚动位置提示。
- 320px 及 390px 视口下，文档不得发生横向溢出；看板和必要的代码区域可在自己的容器中滚动。长用户名、仓库地址、版本内容和错误文案允许换行。
- 加载、空数据、无匹配、权限不足、失败、断线和成功反馈有一致的文案位置与样式。初始加载不伪装成空数据；断线保留最后一次数据并展示最后成功时间。
- 刷新和轮询不得打断当前输入、清空展开表单或抢走焦点；视图切换后页面标题和当前导航状态保持一致。

## 实施边界与结构

沿用原生 HTML、CSS、JavaScript 和现有四个脚本模块。主要修改静态页面结构、CSS 与 UI 渲染；账号中心视图切换归 `accounts.js`，项目视图与卡片归 `app.js`，Git 和 Billing 继续各自拥有数据生命周期。

将 CSS 按 token、基础控件、工作台框架、页面组件、响应式组织，合并重复规则，避免继续在文件末尾层层覆盖。保持现有 DOM ID 和表单字段契约；新增视图必须兼容现有脚本间接口及会话失效保护。

本轮不改变任务状态机、审核权限、付款核验或 API 数据定义；不引入框架迁移、拖拽改变状态、深色主题切换或新增后台能力。三类证据仍分别显示为 agent 自述、本地 Git 观测和 GitHub 验证，合并不等同任务验收。

全部文件保留。测试数据、浏览器证据和本机配置放在 `.local/`，不进入 Git。

## 分阶段交付与验收

1. 设计阶段：确认本提案，记录实施计划并提交文档。
2. 视觉基础与全局框架：统一 token、布局、登录、控件和移动导航，提交源码与相应文档。
3. 工作流完善：团队中心视图、看板与详情、请求／约定／仓库／凭据一致化；行为变化配套有意义的回归验证，分阶段提交。
4. 浏览器验收与记录：使用独立本机测试数据检查 1440px、1280px、768px、390px、320px，覆盖登录、项目选择、看板筛选、任务详情、请求与约定、仓库接入、账单及错误／空状态。

自动验证包括四个网页 JS 回归入口、修改脚本的语法检查和 `test_web.py`。账号视图改动重点覆盖项目／团队切换、退出、权限变化、延迟响应、账单 fragment 与原生弹窗焦点；若修改需要新增行为测试，测试应验证用户可见结果。

验收记录明确区分真实本机服务与合成外部提供方状态，不把 UI 测试当作真实 GitHub 或 Stripe 验收。最终提供前后界面证据、通过的检查、提交信息与仍有的限制。

## 确认点

建议确认方向 A，以及本轮包含账号中心的四个视图和任务详情右侧面板。用户如选择仅做外观精修，可保留现有账号页结构，将信息架构调整移到后续阶段。
