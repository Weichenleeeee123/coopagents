# Git 仓库深度集成提案

日期：2026-10-11。状态：待确认设计，尚未实施。

## 目标与现状

让 Crewmesh 的协作围绕真实仓库展开，建立“任务 → 本地工作区 → 分支 → 提交 → PR → 合并”的可追溯关系。用户继续使用 Claude Code 和 Codex，网页仍是唯一产品工作台；本机首次接入需要配置 agent 连接，日常不要求人手工搬运技术消息或更新看板。

当前 `ActivityStore` 保存调用方提交的仓库、分支和进度字符串，进度来源固定为 `agent_report`；重叠检测比较任务声明的路径范围，没有读取实际 Git 工作区。C1 已有的 GitHub 登录用于账号身份，不等于仓库授权或 GitHub 事件同步。现有项目仍以 `rooms.id` 为内部标识，继续复用团队和项目权限。

## 三种切入方式

| 方式 | 首先解决的问题 | 边界 |
| --- | --- | --- |
| 只接 GitHub | PR、检查和合并状态自动同步 | 看不到各电脑上尚未提交的工作，无法提前提示文件重叠 |
| 只接本地 Git | 仓库识别、分支与工作区绑定、提交前重叠提示 | 本地远程跟踪引用可能过期，不能独立证明当前 PR 或合并状态 |
| 本地 Git + GitHub，分阶段交付（推荐） | 同时覆盖开发中的协作和远端交付证据 | 需要本地适配器及独立的 GitHub App 仓库授权 |

推荐第三种。先做可独立使用的本地接入，再接 GitHub，最后将证据完整呈现在看板。

## 使用流程

1. 项目管理员在网页绑定仓库。首次接入时，本地适配器核对实际仓库与项目绑定；仓库里的配置文件本身不授予项目访问权限。
2. 团队可将不含凭据的 `.crewmesh/project.json` 和 `.crewmesh/rules.md` 纳入版本控制。配置保存格式版本、项目引用和预期仓库；规则记录任务认领、技术约定同步等协作要求。服务地址、令牌、绝对路径、设备标识和同步游标留在本机。
3. 成员在现有 Claude Code 或 Codex 中打开仓库。经过一次接入配置，agent 在任务检查点读取共享约定、待处理消息和其他成员的工作范围。
4. agent 认领任务后，将已有工作区和分支关联到任务。本地适配器采集当前分支、HEAD、变更路径及采集时间；网页显示谁在什么分支处理哪个任务。
5. 两个任务同时涉及同一路径时，显示具体路径和采集时间，提示相关 agent 协商。路径重叠只是风险证据，不直接断言代码冲突或重复实现。
6. push、PR、检查与合并产生新的交付证据。网页显示来源及状态，agent 在下一个检查点读到与自己相关的变化。

这里没有新增编辑器或必需的常驻操作面板。浏览器不能自行读取各电脑的未提交工作；本地能力通过一次配置的适配器提供。空闲会话自动唤醒、所有客户端的实时 hook 触发均不属于已验证能力，首版继续采用检查点拉取。

## 仓库内容与运行数据

仓库承载可评审、可版本化的接入约定。服务保存任务、成员、技术消息、证据和消费状态，避免多人为了发消息或更新状态而反复修改同一份 Git 文件。

本地采集默认只发送 Git 元数据和被 Git 跟踪文件的相对变更路径，不发送源码、diff 正文、提交正文、作者邮箱、绝对路径或带凭据的 remote URL。未跟踪文件路径需用户选择纳入；被忽略文件不采集。网页明确展示采集范围和最后同步时间。

配置文件作为数据解析，不执行其中的命令。仓库指向的服务地址不能触发自动发送凭据；实际服务连接必须来自本机明确建立的信任绑定。已有 `AGENTS.md`、`CLAUDE.md`、MCP 配置及 Git hooks 都要保留，接入时先展示所需的增量改动，不覆盖现有内容。

## 证据与看板状态

| 信息 | 来源标识 | 能证明什么 |
| --- | --- | --- |
| agent 说已完成、正在等待 | agent 自述 | 本次声明及时间 |
| 本地分支、HEAD、变更路径 | 本地 Git 观测 | 该客户端在采集时看到的状态，不是服务端独立验证 |
| PR、远端提交、检查和合并记录 | GitHub 验证 | 已授权仓库中对应对象的远端状态 |
| 任务验收、共享约定批准 | 人工确认 | 有权限成员作出的决定 |

开发状态与交付状态分别保存。合并一个相关 PR 不自动证明整个任务已验收；检查通过不等于代码已合并；旧 HEAD 上的检查不能证明新提交通过。关联对象须带仓库标识、分支或 PR 标识及完整提交 SHA，不能仅凭分支同名关联。

任务可关联多个工作区或交付对象，但只能在权限范围内由任务负责人或项目管理者建立关联。缺少明确任务关系的 PR 放入待关联列表，不靠标题猜测后自动认领任务。GitHub Issue 关联可后续增加；本轮不把 Issue 和 Crewmesh 任务做双向复制。

看板继续按真实进展自动分列、点击详情。保留“阻塞”和“待人工确认”的业务含义；Git 证据丰富任务详情及进度推导，不覆盖人工验收决定。

## GitHub 接入

使用独立的 GitHub App 为选定仓库授予所需的只读权限；沿用现有账号登录机制。绑定时同时验证 Crewmesh 项目管理权限和该安装的仓库访问范围，使用 GitHub 稳定仓库 ID，不以可改名的 URL 作为唯一身份。GitHub 官方文档支持按仓库选择及细粒度权限，适合持续集成服务。[GitHub App 选型依据](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)

处理 PR、push、检查等所需事件，验证 webhook 签名，以 delivery ID 幂等记录，持久化接收后异步处理。收到事件后按需核对当前远端状态，并提供补偿同步，处理乱序、重送、漏收及安装权限撤销。只把鉴权通过并完成校验的数据标为 GitHub 证据。[GitHub webhook 最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

初版不自动创建 PR、改代码、提交、推送或合并。用户原有 agent 仍按用户授权执行这些操作，Crewmesh 负责共享上下文与收集证据。

## 分阶段交付与验收

### G1：仓库接入与本地观测

- 增加仓库绑定、任务与工作区关联领域模型；保持现有未接 Git 的项目可用。
- 提供版本化项目配置、连接诊断及本地适配器。适配器从实际 Git 命令读取元数据，支持普通 clone、linked worktree、detached HEAD 和尚无提交的仓库。
- 使用参数化子进程调用和超时，不拼接 shell 命令，不执行项目自带 hook。Git hooks 仅可作为后续辅助触发器；它们在特定 Git 操作时运行，不能覆盖编辑中的全部变化。[Git hooks 文档](https://git-scm.com/docs/githooks)
- 同步记录包含工作区不透明标识、任务、分支、HEAD、变更路径、采集时间和有效期；过期观测明确标记，不持续冒充活跃开发。
- 用同一电脑上的两个独立 clone/worktree 和两个成员验证：真实路径重叠、断网重试、过期状态、错误项目绑定及跨成员越权。重复请求不制造重复观测；原始证据保留本机。

### G2：远端交付证据

- GitHub App 安装及仓库授权映射；任务明确关联分支、提交和 PR。
- webhook 接收、签名、幂等、重试及补偿同步；检查状态必须关联当前 HEAD。
- 验证跨项目隔离、相同分支名的不同仓库、fork PR、force push、PR 关闭但未合并、旧事件重送及权限撤销。
- 自动测试可覆盖协议和状态机。真实 GitHub App 安装、回调与测试仓库事件另行验收；未完成真实验收前明确标记，不以模拟事件充当上线证据。

### G3：看板和 agent 协作闭环

- 卡片展示任务负责人、分支、同步新鲜度、PR 与检查摘要；详情按时间展示可追溯证据。
- 真实变更路径参与重叠提示，保留与任务声明范围的区别。
- agent 在开始任务、准备改动及提交交付等检查点读取相关消息和最新约定。提问、回应、处理确认继续使用现有机制。
- 验证“一个成员变更共享接口，另一个在检查点读到版本更新；两边交付经 PR 进入网页”的完整流程。
- 同机两成员用于日常回归；实际双机和原生 Claude/Codex 分别记录验收结果与限制。

## 与商业化工作的并行边界

商业化对话正在处理 C2 订阅与额度，本提案单独维护。本次设计草稿不修改订阅、团队、支付、登录或已有公共文档索引。

实施使用独立 Git worktree 和分支，按 G1、G2、G3 分阶段提交代码、测试及文档。Git 集成复用既有账号、团队和项目身份，不新增一套租户系统，不自行定义套餐限制。需要接入现有 HTTP/MCP、数据库初始化或看板的改动在独立分支完成，合并前核对商业化分支的新接口，避免覆盖共享文件。

## 本次需要确认的方向

是否采用“本地 Git + GitHub 双层接入，按 G1 → G2 → G3 推进”。具体客户端触发能力、GitHub App 可用配置和验收结果将进入后续实施计划；本提案不宣称这些能力已经存在。
