# Crewmesh · 同频：产品设计稿

版本：0.2 · 日期：2026-10-10

状态：产品方向、产品形态与名称已确认；进入实施规划。尚未实现产品或完成真实 agent 联调。

品牌名称：**Crewmesh · 同频**。英文文案：**Your agents. One team.** 中文文案：**各自开工，始终同频。** 本次确认为项目名称，不包含域名注册或商标可用性结论。

## 1. 产品定义

让一个小团队各自使用 Claude Code 和 Codex 在自己的电脑上开发同一个 Git 项目时，agent 能共享分工、交换技术信息、跟踪依赖；成员通过一个网页了解进展并处理需要人决定的事项。

核心承诺：保持日常开发方式，在代码汇合之前减少重复劳动、信息过期和人工传话。

用户只需要使用一个产品网页。首次接入允许配置 agent 扩展，后续照常打开原有工具、下指令、开发和提交 PR。网页背后需要协作服务及 agent 端的接入配置；浏览器不能仅凭仓库授权获知尚未提交的本地工作。

## 2. 已确认的使用场景与约束

- 场景来自真实黑客松中的队友协作。
- 每个人使用自己的电脑、自己的 agent 会话和本地仓库，通过分支或 PR 汇合代码。
- 优先支持 Claude Code 和 Codex。
- 用户主要使用 Codex 桌面应用；CLI 也可接受，作为接入验证的备选。
- 产品只提供网页界面，不要求用户改用新的开发界面或统一启动器。
- 允许首次做一次接入配置；日常工作不要求反复手动汇报、检查收件箱或粘贴对方的回复。
- 人继续给自己的 agent 下达目标。agent 可以自动交换任务内的技术信息；涉及分工调整或共同方案变更时，需要明确的人类决定。

首轮验证按两个成员、两台电脑、同一个仓库设计。一人使用 Claude Code，另一人优先使用 Codex 桌面应用。

## 3. 要解决的具体问题

| 问题 | 产品介入时间 | 需要产生的结果 |
| --- | --- | --- |
| 重复实现同一个功能 | 开始修改代码之前 | 看见已有负责人和成果，明确各自的工作边界 |
| 不知道其他 agent 在做什么 | 开始、阶段进展、阻塞、交付时 | 持续更新的任务状态，以及状态来源和时间 |
| 人为技术细节充当传话筒 | agent 遇到跨模块问题时 | 问题直接到达相关 agent，回复回到原任务 |
| 接口或需求变化未同步 | 约定发生变化时 | 受影响方收到变更，并记录接受或处理结果 |
| 依赖无人接住 | 提出依赖、等待回复、无法推进时 | 明确等待谁、等待什么，以及何时需要人介入 |

消息数量不作为价值指标。首版观察人工转述次数、重复工作是否在开工前被发现，以及技术问题是否形成可验证的处理结果。

## 4. 方案选择

| 路径 | 优点 | 代价与限制 | 结论 |
| --- | --- | --- | --- |
| 网页 + agent 扩展 + 在线协作服务 | 保留开发入口，可在提交代码前参与协作 | 需要分别验证两种工具的事件和消息接入 | 首版采用 |
| 网页 + Git 托管平台事件 | 接入相对简单，提交和 PR 有明确依据 | 无法完整了解未提交工作，介入重复劳动较晚 | 用作交付证据的补充 |
| 统一开发或启动界面 | 更容易控制会话运行与消息消费 | 改变已经确认的使用习惯 | 不纳入首版 |

MCP 负责提供协作工具，hooks 负责在支持的工作节点执行同步或提供上下文。二者的角色不同于“无条件唤醒任意会话”，需要按工具、入口和版本验证。

## 5. 主要使用过程

### 5.1 首次加入项目

1. 用户在网页创建项目房间并关联仓库，邀请队友。
2. 队友登录并加入房间；仓库地址用于确认项目，房间成员身份决定访问权限。
3. 网页提供对应工具的一次性接入步骤，完成 MCP、hooks 和协作规则的配置。
4. 接入检查展示实际入口、连接状态和支持的能力；连接成功不等同于已经开始任务。
5. 后续会话自动关联到已连接的仓库和项目房间。同一人同时运行多个会话时分别记录。

本地目录可以各不相同。项目身份使用房间 ID 和仓库映射，不能用某个人电脑上的绝对路径作为团队共同身份。

### 5.2 开始工作与避免重复

1. 用户照常给自己的 agent 下达任务。
2. agent 在进入实现前，读取相关团队任务及已确认约定，声明自己的目标、范围和预期产物。
3. 相同任务的认领由服务端统一处理，避免两个会话同时成功认领同一个任务。
4. 对名称不同但目标相近的任务，系统给出“可能重叠”提示，并说明依据。
5. agent 交换已有进展，提出继续分工、复用成果或合并任务的建议。改变已分配职责需要相关成员明确确认。

重复检测以目标、模块、接口和已有产物为依据。同名文件只是线索；不同分支编辑同一文件可以是合理并行工作。首版不承诺自动发现所有语义重复。

### 5.3 技术问答与依赖

1. 发起方提出具体问题，附上任务、涉及的接口或模块，以及解决问题所需的最小上下文。
2. 根据任务负责人或模块声明找到接收方。无法确定时进入“待指定负责人”，并显示在网页。
3. 接收方在可处理的工作节点读到请求，基于自己的实现或文档回复。
4. 回复包含依据及适用版本；发起方记录是否接受、是否需要修改、修改是否完成。
5. 接收方暂时无法回答时，明确反馈原因或依赖，避免沉默被当作处理完成。

“已送达”“已回应”和“问题已解决”是不同状态。回答被双方确认后可形成项目约定；探索性讨论不会自动升级为团队统一方案。

### 5.4 约定变更与交付

接口约定记录版本、状态、负责人、相关任务和证据。改变共同约定时先发布提议；相关成员确认后生成新版本，并通知依赖它的任务。

交付分别记录：

- 本地实现完成：agent 在本机会话中报告，其他成员未必能取得代码。
- 已推送：对应提交可从远程仓库取得。
- PR 已创建：可以审阅，但不代表已经合并。
- 已合并：代码已经进入目标分支。

例如：“支付接口约定 v2；实现位于 feature/payment 分支的指定提交；已推送，尚未合并。”分支名作为入口，提交标识或约定版本用于锁定消息的适用范围。

## 6. 网页提供的信息

网页围绕项目概览组织，详情按需展开。

### 团队工作状态

每个会话显示成员、agent 工具、当前任务、分支、最近进展、依赖对象和最后更新时间。成员与会话分开建模，一名成员可以拥有多个 agent 会话。

### 需要处理的协作事项

集中展示可能重复的任务、没有负责人的问题、未处理的约定变更，以及需要人确认的分工或方案调整。每条事项包含具体问题、影响范围和可采取的动作。

### 任务详情

展示任务目标、负责人、进展依据、相关问答、约定版本及提交或 PR。人可以查看完整的协作讨论；首页只呈现当前结论。

状态必须区分来源：agent 自述、已观察到的工具事件、Git 证据或人工确认。没有证据时不展示推测的完成百分比。

## 7. 自动协作的边界

默认可以自动执行：

- 发布与更新当前任务范围内的工作状态。
- 读取相关任务、约定和协作请求。
- 询问或回答技术细节，附上适用版本和依据。
- 提示任务重叠、报告阻塞、通知已确认的变更。

需要人明确决定：

- 改变已经分配的职责，或停止某个成员原本安排的工作。
- 采纳会改变共同技术方案或接口约定的提议。
- 解决双方无法达成一致的分工或方案问题。

第一版中的技术问答可以引用已确认的接口事实，不需要对每次回复单独审批。网页上的决定会反馈给相关 agent，并保留作出决定的人、理由和时间。

协作消息保留真实发送者，作为项目资料与请求交给接收方；不能伪装成接收方使用者的指令。接收方仍遵守原有工具权限和任务边界。

## 8. 系统组成及职责

| 组件 | 职责 | 主要依赖 |
| --- | --- | --- |
| 网页 | 房间加入、团队状态、协作详情、人类决定 | 协作服务 API |
| 在线协作服务 | 成员身份、任务认领、消息存储与路由、约定版本、状态事件 | 持久化存储 |
| Claude Code 接入 | 暴露协作工具，在支持的事件节点同步消息和进展 | MCP、hooks、项目协作规则 |
| Codex 接入 | 同上；优先验证桌面应用，必要时使用已接受的 CLI 备选 | MCP、hooks、具体入口及版本 |
| Git 证据接入 | 读取分支、提交和 PR 状态，校验交付信息 | 已授权的仓库数据 |

代码继续通过现有 Git 工作流共享。协作服务保存任务、消息、必要的片段和代码引用；首版无需上传完整本地仓库或全部个人会话。

最低数据对象为：项目房间、成员、agent 会话、任务、协作请求及消息、约定版本、人工决定。每个对象都具有项目归属，关键状态变化有时间和来源记录。

## 9. 消息与状态可靠性

- 消息先持久化，再尝试交付；每条消息具有稳定 ID，重试不会生成重复事项。
- 消息记录“已保存、已交付到会话、已确认、已解决”，交付记录不能代替接收方的处理反馈。
- 通过实际可用的 hooks、协作工具调用及其他已验证机制消费消息。具体接入节点属于技术验证内容。
- 会话闲置或退出时保留消息。没有消费机会时，网页显示等待状态，不宣称 agent 已看到或正在处理。
- 重连后按消息游标恢复未处理内容；旧回复与旧约定版本保持关联，避免覆盖新决定。
- 每张工作卡显示最后更新时间；无新事件时呈现最后已知状态。连接存活不等于 agent 正在执行任务。
- 接入或网络失败时明确标记“协作状态未同步”。用户可继续原有本地工作，但团队协调保证暂时失效。
- 没有负责人、收到阻塞反馈或形成循环依赖时，生成一个需要处理的事项；相同问题不反复广播。

首版支持异步协作。会话关闭时不启动新的 agent；所有会话都没有可用消费节点时，系统不能保证继续自动问答，这一限制必须在网页中可见。

## 10. 第一版范围

包含：

- 项目房间、成员邀请与两种 agent 的一次性接入。
- 会话身份、任务意图、任务认领及状态更新。
- 明确任务冲突检测，以及可解释的潜在重复提示。
- 定向技术问答、依赖状态、简单接口约定和版本变化通知。
- 网页中的工作状态、协作详情及人工决定。
- 分支、提交与 PR 引用，消息重试、断线后的状态恢复。

暂缓：

- 自动合并 PR、自动解决代码冲突或替队友修改分支。
- 统一运行所有成员 agent 的调度器。
- 在会话退出后自动启动 agent，或承诺所有工具都能立即响应消息。
- 通用团队聊天、复杂项目管理、完整个人会话镜像。
- 全量跨工具兼容和企业管理功能。

## 11. 最小验证与验收

首先验证接入，再扩展页面和协作能力。官方存在接口只证明有实现路径，不代表产品已在目标入口运行成功。

### 接入验证

在两台真实电脑上，记录工具入口与版本，完成以下检查：

1. Claude Code 和 Codex 能分别连接同一房间，展示正确的成员、会话和仓库身份。
2. 用户使用日常入口开始任务时，能够获取团队相关状态并发布工作意图。
3. 工作中的接收方在无需人手动粘贴或提醒检查收件箱的情况下处理一次技术请求。
4. 关闭再打开会话后，未处理消息仍可恢复，并且不会被错误标记为已解决。
5. 优先在 Codex 桌面应用完成上述验证；如桌面入口存在限制，记录限制并使用 CLI 进行备选验证，结果明确标注实际入口。

### 协作演示

| 场景 | 通过条件 |
| --- | --- |
| 两边收到相同功能任务 | 后认领者在实现前获知已有任务；同时认领同一任务不会产生两个有效负责人 |
| 技术细节传递 | 一方提出接口问题，另一方回答，原任务收到并确认；过程中没有人转述技术内容 |
| 接口变化 | 变更关联到新版本，受影响任务收到通知，并明确反馈是否完成适配 |
| 一方离线 | 网页显示等待；重新接入后继续处理，消息不丢失、不重复结案 |
| 看板准确性 | 人能看清谁在做什么、依赖谁、最后更新时间及依据；本地完成与已合并不混淆 |

验证时记录重复实现是否已经发生、人工转述次数、问题提出到解决的耗时、等待消费的时长及误报的重复任务。这些是待测指标，不预先宣称有固定的效率提升。

### 关键失败条件

- 只有更换日常启动入口或每次手动提醒才能协作，却仍宣称完全保持原使用习惯。
- 只展示 agent 聊天，没有任务归属、版本或处理反馈。
- 把连接成功、消息送达或 agent 自述当作任务已经完成。
- 仅展示脚本伪造事件，没有在真实 Claude Code 和 Codex 会话中验证。

## 12. 首轮技术验证需要回答的问题

这些问题已有处理路径，不作为隐藏的功能承诺：

| 验证问题 | 验证方法 | 若结果不满足预期 |
| --- | --- | --- |
| Codex 桌面能否完整使用需要的 MCP 和 hooks | 在当前桌面版本测试接入、事件、上下文和回复 | 记录差异，以 CLI 验证备选，并收窄支持声明 |
| 活跃会话能否及时消费协作请求 | 两台电脑互发请求，记录事件节点和处理时间 | 优化受支持的接入节点；未通过前不承诺自动问答体验 |
| 开工前认领是否稳定发生 | 多次从真实用户任务开始观察首次写入与认领顺序 | 调整协作规则与事件接入，保留未同步标记 |
| 潜在重复提示是否有价值 | 测试相似目标、合理并行和不同分支同名文件 | 先保留明确冲突；降低推测性提示的干扰 |
| 问答是否形成空等或来回确认 | 测试离线、无法回答和循环依赖 | 显式阻塞并交给对应成员处理 |

完成接入验证后再确定具体实现框架。当前设计先固定组件职责、数据边界和验收要求，避免技术选型掩盖接入可行性。

## 13. 参考依据

以下官方文档用于说明接入路径，查阅日期为 2026-10-10。工具版本、入口差异与实际可用性仍以实测为准。

- [Claude Code MCP](https://code.claude.com/docs/en/mcp)：协作工具与服务接入。
- [Claude Code hooks](https://code.claude.com/docs/en/hooks)：在工作事件节点执行同步及提供上下文。
- [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)：工具与远程服务连接。
- [Codex hooks](https://learn.chatgpt.com/docs/hooks)：本地会话的事件接入及上下文机制。
- [Claude Code channels](https://code.claude.com/docs/en/channels)：运行中会话的主动事件能力；具有启用方式和可用性限制，不作为首版跨工具通用前提。

已有产品参考：[MCP Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)。其 agent 消息和工作范围声明与本产品相关；本设计重点验证多人分别使用本地工具时，网页可见性与协作结果能否减少人工传话和重复劳动。本文不据此宣称市场上不存在相同方案。
